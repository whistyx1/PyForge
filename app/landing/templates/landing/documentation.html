PYFORGE PROJECT PREVIEW

The deployment workflow we are building.

Today, you can explore a browser-only setup prototype. PyForge does not yet analyze or deploy visitor projects; the workflow below describes the intended product.

Planned: local-first by design

The intended tool will analyze your project locally, prepare a deployment plan, and connect to your Linux server over SSH only after your review and approval. The current setup preview does not make that connection.

What works today

The setup page lets you try project-source selection and server-detail fields in your browser. It does not upload files, analyze code, check a server, create Docker configuration, or deploy an application.

Target frameworks

PyForge is being designed for common Python web projects. Framework detection and project-specific settings are planned.

Django

Detect the project and dependencies, then let you confirm the start command, port, environment, and health check.

Django · Docker Compose

FastAPI

Support ASGI applications and confirm the application command, port, environment, and health-check endpoint.

ASGI · health check

Flask

Analyze the project and let you confirm its WSGI start command, port, and deployment settings.

WSGI · SSH deploy

What the planned workflow will need

Your application

  • A Django, FastAPI, or Flask project provided as a folder, ZIP archive, or public Git repository.
  • A start command, listening port, required environment variables, and health-check path to review or confirm.
  • A database only if your application needs one; PostgreSQL is optional.

Your deployment target

  • A Linux server you control.
  • Docker installed on that server.
  • SSH access so PyForge can run the approved deployment steps and check the server.

Planned deployment workflow

  1. 1. Connect your project

    Choose a project folder, ZIP archive, or public Git repository.

  2. 2. Review detected settings

    Confirm the framework, dependencies, start command, port, environment variables, health check, database choice, and server target.

  3. 3. Inspect the deployment plan

    Review the generated Dockerfile, Docker Compose configuration, and ordered server commands before anything runs.

  4. 4. Approve and deploy

    The planned tool will check the Linux server over SSH, then execute only after you approve the plan.

  5. 5. Check the result

    Review deployment logs and the application's health status after startup.

Your project. Your server. Your control.

The intended workflow targets a server you own and manage. It will keep the target explicit, make commands reviewable, and require approval before deployment actions. Optional PostgreSQL support is planned.
